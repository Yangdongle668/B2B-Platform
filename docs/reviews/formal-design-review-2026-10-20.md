## 1. 结论依据

需求和模块文档已经具备评审所需的结构与覆盖范围。模块分层、站点隔离、发布快照、对象化引用、中文源语言、SSR与询盘目标相互吻合；17份描述符的Schema、依赖DAG、96个权限码、36个组件类型和238条模块验收项通过静态核对。它们足以组织工程验证。

但“11项问题已有统一方案”只证明方案已写出。此次语义审查发现，部分补充方案与原DDL、事务失败行为及旧接口描述没有完全对齐。上一轮静态检查没有验证这些语义，不能据其通过结果宣布契约可冻结。下列DR-01～DR-04必须先整改；DR-05～DR-06必须在M0冻结关卡取得证据。P2可按指定阶段跟踪。

本报告只提出整改要求及关闭判据；跨模块契约的唯一正式定义仍是[平台框架](../framework/platform-framework.md)，表结构仍由所属模块维护。评审意见不另建一套API签名，也没有静默改写源设计来隐藏发现。

## 2. P1：阻塞契约冻结的问题与前提

### DR-01：人工审校策略的字段归属与写入聚合不一致

- **证据**：[content 4.3.1](../modules/content.md)第429/451行及translation 3.2把字段定义为`cnt_content.translation_review_required`；[框架4.10.7](../framework/platform-framework.md)第7441行却要求写`cnt_localization.translation_review_required`，并按本地化version更新。实际MySQL建表后只有cnt_content存在该列。
- **影响**：照补充方案实现会读写不存在的列；若擅自新增列，又会形成内容级和语言级两套审校真值。legal模板切换、目标语言初始化、旧翻译完成事件的发布授权均受影响。
- **整改建议**：优先保留现有DDL的内容级共享策略，由框架统一写入聚合、锁顺序、策略版本以及对各本地化旧审批/自动发布的失效方式；LocalizationInfo可读取内容策略的投影。若确需按语言存储，先明确产品规则并同步content的DDL和ADR，不允许实现方自行选表。
- **关闭证据**：同一字段只有一个权威归属；框架/模块/ADR-024/testkit一致；覆盖legal创建、模板变更、目标语言初始化与晚到事件的并发用例。
- **责任 / 截止**：架构、content/page/translation负责人；M0冻结前。原问题映射：content #1。

### DR-02：媒体回收站与物理删除混为同一步骤

- **证据**：[media 4.3.2、6.1](../modules/media.md)第334/375/604行规定移入回收站、30天后才连同文件物理删除；[框架4.10.1](../framework/platform-framework.md)第7320～7321行以“删除后行读不到”和“提交后删对象”解释统一删除。
- **影响**：软删除后行仍存在，不能用“读不到行”证明并发安全；若移入回收站即删除对象，会破坏恢复能力。
- **整改建议**：分别规定移入回收站、恢复和到期物理清理。引用登记在共享锁内明确校验`deleted_at IS NULL`；移入回收站只改变数据库状态并撤销可用性，不立即删除可恢复的文件；到期清理才执行可重试对象删除。明确业务私有附件的强制清理例外，不能绕过受保护资产引用。
- **关闭证据**：保存与软删除竞争的双方结果明确；回收站内对象不能被新引用；30天内恢复可用；物理清理失败重试不破坏元数据/对象的一致性。
- **责任 / 截止**：media、core及源保存入口负责人；M0冻结前。原问题映射：MEDIA-02、ADR-019。

### DR-03：下载留资失败的事务语义相反

- **证据**：[form 5.2](../modules/form.md)第727行要求“签名失败不撤销已保存提交”；同文5.3及[框架4.10.6](../framework/platform-framework.md)第7431行要求提交、票据、发件箱同事务回滚。旧流程允许“非REJECT”，新流程禁止QUARANTINE发下载邮件，需明确票据是否同样禁止。
- **影响**：前端重试、幂等命中、询盘事件、邮件入队会因开发者选择不同段落而产生不同结果。返回失败但提交仍存在，以及返回成功但没有可恢复发送义务，是两种不同产品行为。
- **整改建议**：将成功判据、ACCEPT/QUARANTINE/REJECT/测试提交的票据和邮件矩阵、签名/模板/发件箱失败的响应与补偿统一到框架；再删除相反描述。优先走已提议的同事务提交/入队，但签名票据如果无持久记录，只能保证提交前不外泄，不能含糊承诺“撤回已发出的签名”；需明确票据存储及撤销模型。
- **关闭证据**：一个失败矩阵、一个幂等结果定义；签名失败/模板缺失/数据库回滚/客户端超时重放各有唯一预期；SMTP结果与数据库提交结果分开。
- **责任 / 截止**：form/media/notification负责人；M0冻结前。原问题映射：FORM-01、ADR-023。

### DR-04：新增方案与旧接口/事件/缓存规则仍并存

- **证据**：[框架4.6.6、4.6.7](../framework/platform-framework.md)第5650/5753行仍让media异步整组替换导航/站点资料引用，13.2集成耦合表仍由media收集Collector；4.10.1要求源事务登记并禁止旧异步写入。content 5.2和框架4.5.20仍允许翻译无expectedVersion回写，4.10.7却要求共同版本检查。8.3.11还保留86400秒及七天stale动态缓存示例，4.10.3要求freshUntil预算并禁止stale扩展。
- **影响**：接口真实实现、替身和前端缓存可以分别遵守不同版本的描述，局部测试通过却无法保证组合行为。
- **整改建议**：把确定方案并回完整接口、Javadoc、事件发布/订阅总表、各模块2.2/2.4/2.6/5/12/14章、前端响应头及集成表；旧规则删除或明确只作历史记录。版本检查还需有实际可传递的当前目标版本与失败码，不能只在补充章节写一句“要校验”。
- **关闭证据**：逐入口追踪表中每一行为只有一份有效定义；真实实现与替身执行相同故障时序；本报告列出的旧路径无有效实现入口。
- **责任 / 截止**：框架负责人及涉及模块负责人；M0冻结前。映射：ADR-019/020/024及原11项的文档同步。

### DR-05：搜索代次方案尚缺容量与延迟的采纳证据

- **证据**：[框架4.10.4](../framework/platform-framework.md)和[ADR-021](../adr/0021-immutable-search-generations.md)要求每批增量复制不可变索引代次，代价O(N)；每个源事实事务还要串行取得同语言控制行锁。现有证据只有建表成功，没有引擎/负载运行结果。
- **影响**：以某一语言N=15000条、批内k=1条变更为例，理论复制文档量相对于变化量约为15000倍；这是算法成本说明，不是实测耗时。突发发布时可能持续追不平，无法证明满足网站更新需要。
- **整改建议**：冻结前做隔离PoC，约定搜索可见延迟、突发积压恢复时间、CPU/内存/磁盘上限；用1万产品、5千文章、单语到10语、持续更新/下线/改路径验证。记录旧worker迟到、未知受理、指针CAS与GC结果。若成本不合格，在ADR层比较替代方案，不退回缺少恢复证明的原地写入+租约。
- **关闭证据**：ADR-021明确采纳/修改结论和真实报告；源事务P95、搜索延迟、复制吞吐、日志增长、故障恢复达到预先约定标准。签名可先RC验证，不能把M4业务实施时才做首次架构容量验证。
- **责任 / 截止**：架构、search/infrastructure负责人；M0整体契约冻结前完成采纳验证，M4复测业务规模。

### DR-06：版本组合与正式决策尚未形成可发布基线

- **证据**：[ADR-011](../adr/0011-technology-versions.md)的版本表仍是“待M0验证”；26份ADR中5份Accepted、21份Proposed，新增7份只是后者的一部分。[框架13.1](../framework/platform-framework.md)要求全部V1契约、替身、边界CI和版本验证就绪，目前无工程骨架或真实CODEOWNERS人员。
- **影响**：不能把文档评审直接转换成platform-api 1.0.0发布；技术组合、权限/事件基础机制或审批边界变化会影响全部模块。
- **整改建议**：按决策依赖把现有Proposed划分为M0必须采纳、后续阶段采纳以及业主自管部署/法务事项；不能把21项全部当同等开工阻塞。完成Boot/Modulith/MyBatis-Plus/Flyway/Nuxt兼容性冒烟，登记实际负责人并按仓库要求签审。ADR-015/016的业主自管边界保留，不增加本次审批要求。
- **关闭证据**：版本锁定、相关ADR状态和变更记录、可启动骨架、全部契约/替身测试、边界反例CI、所需人工评审记录。
- **责任 / 截止**：架构/框架负责人；M0结束前。允许M0工程验证先行，不允许据此宣称业务模块DoR满足。

## 5. 验证结果和证据边界

| 检查 | 结果 | 能证明 / 不能证明 |
|---|---|---|
| 52份源文档快照 | 路径、行数、SHA-256已记录 | 精确标识评审对象；不能覆盖后续修改 |
| 17份描述符 | JSON Schema、依赖DAG、权限/菜单/组件唯一性通过 | 结构一致；不代表ADR已采纳或事务语义一致 |
| 接口/验收清单 | 234条Admin端点、96权限、36组件、238条模块验收；另25条故障要求 | 是需求数量，不是已实现/已通过测试数量 |
| 文档引用/章节 | 完整当前54份Markdown中的248处本地链接/锚点通过；评审源快照仍为52份 | 文件/锚点存在；不代替字段、锁、事务语义审查 |
| MySQL空库 | **MySQL 8.4.11：119个CREATE块成功，119张表建成，失败0；foreign_key_checks=1** | DDL语法、建表顺序及外键DDL可被引擎接受；不证明跨站业务检查、迁移升级或并发协议正确 |
| 审校字段实库观察 | 仅cnt_content有translation_review_required | 直接支持DR-01；“建表全过”不能排除字段归属冲突 |
| 应用/基础设施/浏览器 | 未执行 | 未验证Boot组合、Flyway迁移、Redis/Meilisearch/SMTP、E2E、权限/站点隔离、可访问性、性能及故障注入 |

SQL来源仅为平台框架与模块权威DDL；系统设计中的示意DDL不重复建表，2个非CREATE SQL示例未执行。按REFERENCES依赖排序，未关闭外键检查、未改写源SQL；镜像digest与逐块结果见证据文件。使用不开放端口、无外部网络的临时容器，检查后清理；没有连接或修改业务数据库。

首次探测曾命中镜像初始化临时socket服务，产生连接失败；随后改为正式TCP就绪检查并清空复跑。上表只采用完整复跑结果，没有把初始化连接失败记为设计缺陷，也没有掩盖真正的SQL错误。

## 6. 开发准入与复审安排

1. 立即可做：DR-01～04设计整改、DR-05/06隔离验证、UI样稿与素材准备、评审基线整理。
2. M0冻结关卡：P1关闭并复审，相关ADR完成所需签审；全部V1契约和testkit可用，版本组合/边界CI/本地启动有真实记录。
3. M1～M4：按[开发流程与任务计划](../plans/development-plan.md)逐条业务链交付，每个模块切片先满足DoR，再以真实实现替换替身验收。
4. 关闭记录填写证据PR/测试报告和复审人；没有真实执行就标“未验证”。本报告不替代仓库29.4/框架4.9规定的人工PR评审，也不改变V1=M1～M4的范围。

本轮没有将任何ADR或模块状态改为Accepted/已评审。复审需要确认的是整改后的具体基线，而不是再次确认是否需要评审。
