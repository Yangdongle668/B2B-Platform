## 背景

平台的定位是“让 B2B 制造与贸易企业用搭积木的方式运营一个设计专业、SEO 自动维护、能持续获取海外询盘的官网”（1.1）。与传统 CMS 的差异集中在五点：

1. **SEO 原生**：URL、Meta、Schema、Sitemap、hreflang、内链由系统自动维护，人工只做覆盖（13、14）；
2. **内容关系驱动**：新增内容自动与已有内容建立关联并生成内链（Content Graph，15）；
3. **设计系统驱动**：运营只能在设计系统的约束内选择组件与变体（10、11）；
4. **获客闭环**：从访问来源到询盘、分配、通知、跟进全链路可追踪（17、20）；
5. **模块化**：CRM、报价、WhatsApp、AI 等能力以模块形式增加，不改动内核（3）。

约束：

- 自用，一家企业、多个站点（A1，见 ADR-009）；团队 2–6 人，Java + Vue 技术栈，使用 Claude Code 辅助开发（A6）；多数情况需要从旧站迁移内容与 URL（A7）。
- 内容以简体中文录入，其他语言由 AI 翻译生成（V1.3，见 ADR-005、ADR-017），翻译需要深入内容模型（翻译单元、翻译记忆、布局同步）。

需要回答的问题（32 章 Q12）：自研，还是基于现有的 Headless CMS 二次开发？V1.2 已确认自研。

## 决策

**自研。** 不基于现有 Headless CMS 二次开发。

- 后端为 Spring Boot 模块化单体，前台为 Nuxt SSR，后台为 Vue 3 SPA（2.1、2.4）；内容内核、URL 与 SEO 引擎、Content Graph、页面编辑器、模块机制、AI 翻译均由本项目实现。
- “自研”指平台本身，不指重复造通用轮子：通用能力使用成熟的开源组件，如 Spring Modulith（模块边界验证、事件发布登记）、MyBatis-Plus、Flyway、Meilisearch、imgproxy、Tiptap、Style Dictionary（2.4）。引入新的基础设施依赖仍需要 ADR（29.5）。
- 代价（内容内核与页面编辑器的工作量）通过以下手段控制：
  - 严格的 V1 范围（1.4）：不做热插拔、自由布局、多级审批、实时协同等；
  - 垂直切片的里程碑 M0–M5，每个里程碑都有可演示、可验收的完整链路（30）；
  - M1 先用 PRODUCT 一种类型验证“快照 + 投影”模型，M2 再推广到其他类型（30、31）；
  - 页面编辑器只做 Section 级编辑与预设变体，不做自由布局（1.4、31）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 基于现有 Headless CMS 二次开发 | 内容建模、后台、API 现成，起步快 | SEO 引擎、内容图谱、模块扩展需要深度定制，受制于其数据模型与扩展机制，难以做到“系统自动维护、人工只做覆盖”；技术栈与团队的 Java 技术栈不一致；升级时定制部分容易冲突 | 不采用 |
| Headless CMS 管内容 + 自研服务管 SEO、图谱、询盘 | 内容管理现成；核心能力仍可自研 | 两套数据模型与权限体系，需要双向同步；发布要求“发布成功即可被路由”的强一致（4.4）难以跨系统保证；形成分布式系统，运维成本高 | 不采用 |
| 基于传统 CMS（如旧站常用的 WordPress） | 生态、主题丰富，便于迁移旧站 | 技术栈不一致；SEO、页面搭建依赖插件组合，行为难以统一受控；难以落实设计系统约束与模块边界 | 不采用（旧站只作为迁移来源，见 13.5） |
| 自研 | 核心能力完全可控；与团队技术栈一致；架构规则可以自动化检查 | 内容内核与页面编辑器工作量大 | 采用 |

## 后果

### 正面

- SEO 引擎、Content Graph、模块机制、AI 翻译可以按 1.1 的定位深度设计，而不是在第三方模型上打补丁。
- 前后端技术栈统一（Java + Vue），与团队技能和 Claude Code 辅助开发的方式一致。
- 架构原则 P1–P8 可以从第一行代码起由 CI 自动守护（29.3）。
- 数据模型（站点、本地化、修订、快照、投影、翻译状态）从一开始就按需求设计（ADR-004、ADR-009）。

### 负面与代价

- 内容内核、页面编辑器、媒体、预览、审核、回收站等通用 CMS 能力都要自己实现，工作量大（2.5）。
- 相关风险：自研工作量超出预期、页面编辑器复杂度失控、内容内核设计错误导致返工（31）。
- 长期维护完全由团队承担；第三方依赖的版本兼容需要自己验证（ADR-011）。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 新功能先对照 V1 范围（1.4）；超出范围的放到 V2+，或经评审调整范围 | PR 评审；里程碑复盘 |
| 通用能力优先使用成熟组件；引入新的基础设施依赖先写 ADR | PR 评审（依赖变更）；29.5 |
| 每个里程碑结束时演示并复盘，必要时调整后续范围；工作量超出预期时，把 M4 中的部分功能移到 V2 | 里程碑验收（30、31） |
| 内容内核先用 PRODUCT 验证再推广 | M1 验收（30） |
