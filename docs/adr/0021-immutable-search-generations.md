## 背景

引擎 upsert 没有 CAS，旧 worker 迟到可能覆盖新文档；swap 返回丢失后盲目重放会把索引换回去。

## 决策

源事务经 core SPI 在 search 自有 sch_ 表登记变更序号；每次构建使用唯一私有代次，追平后按源变更序号、构建 fence 和活跃版本 CAS 切换数据库指针。已发布代次不可写，V1 不调用 swap。

完整签名、事务边界、失败恢复与适配器约束统一在[平台框架 4.10.4](../framework/platform-framework.md)登记。本 ADR 解释决策理由，不另建跨模块契约定义。问题映射和故障验收见[处理说明](../reviews/design-issue-resolution-2026-10-20.md)。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 本文方案 | 明确事实提交和派生状态的边界，可恢复、可测试 | 新增3张持久控制表和备份责任；增量代次复制有 O(N) 写入成本，需要基线压测，优化不能取消一致性屏障。 | 提议采用，待评审 |
| 原索引增量写入 + Redis 租约 + swap | 初期改动较少 | 租约丢失无法阻止外部引擎的迟到写入；原子交换本身不是可安全重放的幂等操作。 | 不采用 |

## 后果

### 正面

- 将 SEARCH-01 从笼统待定项整理为具体设计，保持业务模块只访问自己的表。
- 并发、重试和宕机结果可由数据库/端口行为验证，不以文档审查代替运行测试。

### 负面与代价

- 新增3张持久控制表和备份责任；增量代次复制有 O(N) 写入成本，需要基线压测，优化不能取消一致性屏障。
- 新增契约、真实实现、替身及契约测试需同批实现；本仓库尚无代码骨架。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 只通过平台框架登记的契约协作；站点边界不变 | 架构负责人评审、ArchUnit、Modulith verify |
| 必须执行本方案的并发/故障时序 | 处理说明中的契约、集成与故障注入用例 |
| ADR 不自动获得 Accepted 状态 | 按 [ADR 流程](README.md)及框架 4.9 评审；此轮仅起草方案 |
