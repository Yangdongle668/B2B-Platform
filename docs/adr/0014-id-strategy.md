## 背景

- 后端是多实例部署的模块化单体（27.1：后端 × 2+），所有实例都会创建数据。
- 很多场景需要在写入数据库之前就知道 ID：
  - 业务模块在自己的事务中调用 `ContentApi.create(type, locale)` 获得 `content_id`，再写入本模块的表（6.1）；
  - 事件在业务事务内发布，携带 `eventId` 与相关对象的 ID（4.2、ADR-003）；
  - 媒体的存储键为 `{siteId}/{yyyy}/{mm}/{id}-{slug化的原文件名}.{ext}`（12.2）。
- 跨模块引用只保存 ID，不建外键（25.5、ADR-002）；快照与布局文档对其他对象只保存 ID（`$content`、`$media`、`$term`），富文本中的链接为 `content://{id}`（6.4、10.3、14.8）。ID 在快照、布局文档、事件、缓存标签与 URL 中长期保存，一旦确定不能改变。
- 数据库为 MySQL 8.4 InnoDB（25.1），主键即聚簇索引，主键越大、越随机，插入与二级索引的成本越高。
- 前台（Nuxt）与后台（Vue）都使用 JavaScript：`Number` 只能精确表示 2^53 − 1 以内的整数，64 位整数直接作为 JSON 数字传递会静默丢失精度。

## 决策

1. **主键使用 64 位 TSID**（时间有序的 64 位 ID）：表的主键为 `id BIGINT`，由应用生成，不使用数据库自增（25.3）。跨模块引用字段（如 `content_id`、`media_id`）同样为 `BIGINT`，保存被引用对象的 TSID。
2. **事件 ID**：`DomainEvent.eventId()` 为 TSID（4.2），监听器按它去重（ADR-003）。
3. **JSON 中一律序列化为字符串**（24.2）：后台 API、公开 API、Delivery API、快照、布局文档中的所有 ID 都是字符串；Java 代码内部使用 `long` / `Long`。例如：

```json
{
  "content": { "id": "7201893453912345", "type": "PRODUCT" },
  "image":   { "$media": "7201893453918208" },
  "refs":    { "media": { "7201893453918208": { "width": 1600, "height": 1200 } } }
}
```

4. **OpenAPI 与前端类型**：OpenAPI 文档中 ID 字段声明为字符串，`openapi-typescript` 生成的类型为 `string`（24.3）；前端把 ID 当作不透明的字符串处理，只做相等比较，不做数值转换或运算。
5. **不属于本 ADR 的标识**：布局文档中 Section 的 `id`（如 `sec_01J9X4K2`）是文档内的稳定标识（10.3）；同意记录的 `consent_id` 为随机生成的假名标识（20.2）；预览令牌为签名令牌（6.5）；AI 翻译请求中的单元 ID 由系统按请求生成（5.9）。它们都不是数据库主键。系统操作的 `created_by` / `updated_by` 为 0（25.3）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 数据库自增 ID | 简单、紧凑、连续 | 写入之后才有 ID，与“先取得 `content_id`、先确定存储键”冲突；暴露数据量与增长速度；不同环境或实例之间导入导出时容易冲突 | 不采用 |
| UUID v4 | 应用生成，全局唯一 | 128 位，随机分布导致聚簇索引页分裂；每个二级索引都包含主键，体积大；不易阅读 | 不采用 |
| UUID v7 | 应用生成、时间有序、标准化 | 128 位，存储与索引仍是 BIGINT 的两倍；JSON 中同样是字符串，没有额外收益 | 不采用 |
| 64 位 TSID，JSON 中为数字 | 前后端类型一致 | JavaScript 中超过 2^53 − 1 的 ID 会静默丢失精度 | 不采用 |
| 64 位 TSID，JSON 中为字符串 | 应用生成、时间有序、BIGINT 紧凑；前端不丢精度 | 前后端类型不同，需要统一的序列化规则；多实例需要避免冲突 | 采用 |

## 后果

### 正面

- ID 在写入前即可确定，事务内可以先生成 ID 再写多张表、发布事件、确定存储键。
- 时间有序，InnoDB 主键基本按顺序插入，索引紧凑；BIGINT 比 UUID 节省存储。
- 全局唯一，不依赖数据库序列；将来按“一企业一实例”部署（ADR-009）或在环境之间迁移数据时不会冲突。
- 前端统一使用字符串，不会出现精度问题。

### 负面与代价

- Java 与 JSON 中的类型不同（`long` 与字符串），必须由全局序列化规则保证，个别字段遗漏会在 ID 超过 2^53 − 1 时才暴露。
- 多个后端实例同时生成 ID，生成器必须保证实例之间不冲突（如为每个实例分配不同的节点号）。
- ID 中含有创建时间，可以从 ID 推断对象的创建时间；ID 不是秘密，不能用作访问凭证（未发布内容的保护靠 26.2 的规则）。
- 多实例生成的 ID 只是大致按时间递增，不能用作严格的业务排序依据，排序使用 `published_at`、`created_at` 等显式字段。
- 数字很长，日志与排查时不如自增 ID 直观。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 新表主键为 `id BIGINT NOT NULL`，由应用生成，不使用 `AUTO_INCREMENT` | PR 评审（迁移脚本）；《领域模型与数据库设计》（附录 C） |
| API 响应、快照、布局文档、事件载荷中的 ID 一律为字符串 | 契约测试：OpenAPI 快照 + oasdiff（24.3、28）；组件 Schema 校验（`$content` / `$media` / `$term` 为字符串） |
| 前端不对 ID 做 `Number()`、`parseInt` 等数值转换，不把 ID 当作排序依据 | TypeScript 类型检查（生成类型为 `string`）；PR 评审 |
| 所有模块使用同一个 ID 生成规则，不各自实现 | PR 评审（platform-core / platform-api 的变更需架构负责人审核，29.4） |
| 跨模块引用只保存 ID，不建外键 | 25.5；PR 评审 |
| 不得用 ID 的不可猜测性代替权限或发布状态检查 | PR 评审；26.2 |
