# ADR-001：编译期模块 + 站点级启用开关

| 相关 ADR | ADR-000、ADR-002、ADR-009、ADR-011 |

## 背景

- 平台要求“CRM、报价、WhatsApp、AI 等能力以模块形式增加，不改动内核”（1.1）。
- 一家企业有多个站点（ADR-009），各站点需要的功能不同。验收场景 S10：站点管理员停用“文章”模块后，后台菜单、API、组件面板中不再出现；系统提示受影响的已发布内容；数据全部保留（1.3）。
- 一个模块是一个**纵向切片**，横跨后端 Maven 模块、Admin 中的 `modules/<id>/`、前台主题中的组件、共享 Schema 包中的组件与模板定义四个位置，四者使用同一个模块 ID（3.4）。
- V1.0 设计了运行时热插拔的插件系统。但 Nuxt 与 Admin 无法在运行时加载新组件，热插拔的复杂度与收益不匹配（0.2 第 2 项）；V1 不包含运行时热插拔与第三方模块市场（1.4）。

## 决策

1. **编译期装配**：模块是 `backend/modules/` 下的 Maven 模块，由 `application` 统一装配；Admin 与前台主题中的模块代码同样全部编译在内（Admin 按模块分包、懒加载，22.2）。增加或移除模块需要重新构建与部署。
2. **模块描述符** `module.json`（3.5）：声明 id、名称（中文字符串）、版本、所在层、平台版本范围、`requires` / `optional`（语义化版本范围）、`disableable`、表前缀、API 前缀、权限、菜单、设置 Schema、组件、发布与订阅的事件。权限、菜单等声明式资源在启动时由平台幂等同步。
3. **平台级生命周期**（与代码版本相关，3.6）：`INSTALLING → INSTALLED(vX) → UPGRADING → INSTALLED(vY)`，失败为 `FAILED`（阻止启动）；构建中移除的模块为 `MISSING`（数据保留）；只有系统管理员在所有站点均已停用后显式执行，才进入 `PURGED`（删除数据，需二次确认并先备份）。
4. **启动流程**：扫描描述符 → 校验 ID 唯一、版本范围、无循环依赖 → 获取数据库锁 → 按拓扑顺序执行各模块的 Flyway 迁移（history 表 `flyway_<module>_history`）→ `onInstall` / `onUpgrade` → 同步声明式资源 → 构建扩展点注册表 → readiness 变为 UP。生产环境的迁移由独立的 migrate 任务在滚动更新前执行，启动时的迁移只作兜底（3.6）。
5. **站点级启用开关**：`sys_site_module` 中的 `ENABLED` / `DISABLED`。`disableable = false` 的核心模块不能停用；V1 中可停用的模块为 form、translation、product、article、inquiry、search、tracking（3.2）。
6. **停用即“隐藏而不删除”**（3.8）：

| 对象 | 停用后的行为 |
|---|---|
| 后台菜单与路由、Admin / Public API | 隐藏；API 由 `ModuleGuardFilter` 按 `apiPrefix` 返回 404 |
| 事件监听、定时任务 | 跳过执行；事件本身照常记录 |
| 扩展点 | 注册表不再返回该模块的实现 |
| 前台组件 | 组件面板中隐藏；已放置的实例在前台不渲染，编辑器中显示“模块已停用”占位 |
| 该模块的内容类型 | 停用前展示影响报告（`analyzeDisableImpact`）并要求确认；之后路由返回 404（可选批量 301）；sitemap、搜索、图谱自动排除 |
| 数据 | 全部保留；重新启用后恢复 |

7. **SPI**：每个模块提供 `PlatformModule` 实现（`descriptor`、`onInstall`、`onUpgrade`、`onEnable`、`onDisable`、`analyzeDisableImpact`、`onPurge`，3.6）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 运行时热插拔（V1.0 的插件系统） | 不重新部署即可安装新模块 | Nuxt 与 Admin 无法在运行时加载新组件；类加载、版本隔离、迁移与回滚复杂；复杂度与收益不匹配 | 不采用 |
| 微服务（每个模块独立部署） | 独立扩展、独立发布 | 2–6 人团队的运维成本高；发布需要的强一致（4.4）要跨服务保证 | 不采用（2.1） |
| 编译期模块，不提供站点级开关 | 最简单 | 无法满足 S10 与各站点功能差异 | 不采用 |
| 编译期模块 + 站点级启用开关 | 一次构建，前后端一致；编译期即可检查依赖；按站点启停且数据安全 | 新增模块需要发版 | 采用 |

## 后果

### 正面

- 后端、Admin、前台主题在同一次构建中保持一致，不存在“后端有模块、前端没有组件”的情况。
- 模块之间的依赖在编译期与启动时校验（配合 ADR-002 的编译隔离），问题尽早暴露。
- 停用不删除数据，重新启用即可恢复；删除数据必须显式执行，误操作风险低。
- 新模块的菜单、权限由描述符声明，Core 不需要修改代码（22.2）。

### 负面与代价

- 新增模块必须发版；不支持第三方在运行时安装模块。
- 每次部署都包含全部模块的代码；前端需要按模块分包、懒加载，控制体积。
- 模块管理器（描述符解析、依赖校验、按序迁移、启用开关、停用影响分析）是 M0 的额外工作量。
- 每个可停用的模块都要保证停用时的行为正确（3.8），并需要相应的测试。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 新增模块先写 ADR，并按 29.2 的新模块接入清单接入 | 29.5；PR 评审 |
| 模块的运行时依赖在 `module.json` 的 `requires` / `optional` 中声明；禁止循环依赖 | 启动时校验，失败则阻止启动 |
| `module.json` 中声明的事件与代码一致 | CI 脚本（29.3） |
| 迁移脚本放在 `db/migration/{module}`，命名 `V{三位序号}__{描述}.sql`；已合入的脚本不可修改；遵循 expand / contract | CI 校验迁移文件哈希（25.6、29.3） |
| 停用时的行为依靠平台的统一机制实现（`ModuleGuardFilter`、监听器包装器、扩展点注册表的过滤，3.8）；模块的 API 前缀、菜单、组件必须在 `module.json` 中如实声明，否则这些机制无法生效 | PR 评审 |
| 可停用模块实现 `analyzeDisableImpact` | PR 评审；E2E 场景 S10（28） |
| M0 验收：示例模块违反边界时 CI 失败；按模板新建一个模块并接入不超过 1 小时 | 里程碑验收（30） |
