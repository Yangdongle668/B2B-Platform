## 背景

- V1.0 中 SEO 数据分散在 4 处（0.2 第 6 项），并且存在 Product → SEO 的反向依赖（0.2 第 3 项）。
- 产品定位是“SEO 原生”：URL、Meta、Schema、Sitemap、hreflang、内链由系统自动维护，人工只做覆盖（1.1、P6）。按假设 A4，单站可达 1 万产品 × 多种语言，逐页人工填写 Meta 不现实。
- 人工填写的值必须可靠保留：模板或规则变化时不能覆盖人工值，也要能随时“恢复为自动”。
- 前台只读快照（P4），页面头部信息必须能从发布态数据直接得到，结果与发布时一致、可追溯。
- 模块之间只能通过 `platform-api` 中的契约协作（ADR-002）；附录 A 禁止“SEO 逻辑散落在业务模块中”。
- V1.3：内容以中文录入，其他语言由 AI 翻译生成（ADR-017）；人工覆盖的 SEO 文本同样需要出现在目标语言中，并且受长度限制（如 SEO 标题 60 个字符，5.6）。

## 决策

1. **seo 模块（L4）拥有全部 SEO 数据**（14.1、25.8）：

| 表 | 内容 |
|---|---|
| `seo_meta` | 每个本地化一条（草稿态）：`title_override`、`description_override`、`canonical_override`、`robots_override`、`og_title_override`、`og_description_override`、`og_image_media_id`、`schema_extra`（手工补充的 JSON-LD，仅开发者角色）、`focus_keyword` |
| `seo_template` | 站点 × 语言 × 内容类型的标题与描述模板，如标题 `{title} \| {siteName}`，描述取摘要并截断到 155 个字符 |
| `seo_link`、`seo_audit`、`seo_robots_rule` | 链接索引、健康检查结果、robots 规则 |

2. **业务模块不保存 SEO 字段，也不输出 meta 或 JSON-LD**，只通过扩展点向 seo 提供输入（3.7）：

| 扩展点 | 业务模块提供的内容 |
|---|---|
| `SeoVariableProvider` | 模板变量，如产品的 `{modelNo}`、`{primaryCategory}`、`{brand}` |
| `SchemaOrgProvider` | 本类型的 JSON-LD 节点，由 seo 组装为一个 `@graph`（14.5） |
| `BreadcrumbProvider` | 面包屑路径，同时用于 `BreadcrumbList` |
| `SeoRule` | 本类型特有的健康检查规则（14.9） |

3. **每个字段区分自动值与覆盖值**：
   - 最终值 = 覆盖值 ?? 自动值；自动值由 `seo_template` 与模板变量生成。
   - **自动值永远不会覆盖人工值**；后台可以“恢复为自动”（清除覆盖值）。
   - canonical 默认指向本语言自身的绝对 URL（去除分页以外的查询参数），禁止跨语言 canonical；hreflang 与 `x-default` 由已发布且所属语言“对外公开”的本地化生成，不手工维护（14.2、14.4、ADR-005）。

4. **发布时写入快照**：seo 模块的 `PublishContributor` 计算最终值，把最终值、自动值以及被覆盖的字段列表一起写入快照的 `seo` 部分（如 `"overridden": ["title"]`，6.4）。前台的页面头部（title、meta description、canonical、robots、hreflang、Open Graph、JSON-LD）由 seo 模块的 `DeliveryContributor` 生成，Nuxt 直接输出 Delivery 响应中的 `seo` 部分（14.2、24.4）。

5. **翻译**（V1.3）：源语言的覆盖值（标题、描述、OG 标题与描述）作为翻译单元随内容翻译到目标语言，由 seo 模块实现 `TranslatableContentProvider`（3.7、5.6）；字段的长度上限作为翻译单元的 `maxLength`。没有覆盖值的字段，在目标语言中同样由该语言的模板自动生成。

6. **后台**：SEO 标签由 seo 模块注册到内容编辑外壳（22.3），提供搜索结果预览（按像素宽度估算桌面端与移动端截断）、字数统计与自动值占位提示。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| SEO 字段放在各业务表中（如产品本地化表中的 meta 标题） | 直观，查询简单 | 数据分散（V1.0 的问题）；每个模块重复实现生成、校验与健康检查；业务模块与 SEO 规则耦合 | 不采用 |
| 只保存人工值，前台渲染时临时生成自动值 | 存储少 | 渲染时需要读取模板与业务数据，结果不可追溯；违反“前台只读快照”（P4） | 不采用 |
| 自动值与人工值写入同一个字段 | 字段少 | 模板变化时要么覆盖人工值，要么无法更新自动值；无法“恢复为自动” | 不采用 |
| seo 模块拥有数据，自动值与覆盖值分离，发布时写入快照；业务模块通过扩展点提供输入 | 归属单一；人工值永不丢失；线上结果可追溯；模块之间编译期互不可见 | 业务模块要实现若干扩展点；自动值在发布时冻结 | 采用 |

## 后果

### 正面

- SEO 数据只有一个归属：规则、生成、校验、健康检查都集中在 seo 模块；业务模块与 seo 在编译期互不可见（3.3）。
- 大量内容的 Meta 自动生成，人工只需处理少数重要页面。
- 快照中同时保存最终值、自动值与覆盖字段列表，线上结果可追溯，后台能清楚区分“自动”与“人工”。
- 覆盖值随翻译流程进入目标语言，不需要在每种语言重复填写。

### 负面与代价

- 快照的 `seo` 部分同时保存最终值与自动值，体积略有增加。
- 自动值在发布时计算并冻结在快照中：修改 `seo_template` 或模板变量的来源（如站点名称）后，已发布内容需要重新发布才会更新；批量刷新的方式在《URL 与 SEO 引擎详细设计》中确定（附录 C）。
- 每新增一种内容类型，都要实现 `SeoVariableProvider`、`SchemaOrgProvider`、`BreadcrumbProvider` 等扩展点（29.2）。
- 覆盖值的翻译增加翻译单元，并受长度上限约束：译文超长时自动重试一次，仍超长则标记 `NEEDS_REVIEW`，所在本地化不自动发布，需要人工处理（5.8）。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 业务模块不得新增 SEO 字段或自行输出 `<title>`、meta、JSON-LD，只能实现扩展点（附录 A 禁止 6） | 架构测试：模块之间不互相 import（29.3）；PR 评审 |
| Nuxt 只输出 Delivery 返回的 `seo` 部分，不自行拼接页面头部 | PR 评审 |
| 自动生成逻辑只写自动值，不得写入 `*_override` 字段；快照中的 `overridden` 列表与覆盖值一致 | seo 模块单元测试与模块集成测试（28） |
| canonical 指向本语言自身，禁止跨语言 canonical；hreflang 只来自已发布且对外公开的本地化 | staging 上的 SEO 爬取检查 `tools/seo-check`（28） |
| 各内容类型输出的 JSON-LD 符合 Schema | CI 中的 JSON Schema 校验（14.5）；SEO 健康检查 |
| 新增内容类型实现 29.2 第 3 步中与 SEO 相关的扩展点 | 完成定义（29.6）；PR 评审 |
| 新增可翻译的 SEO 字段时，在 seo 模块的 `TranslatableContentProvider` 中登记 | 完成定义（29.6）；PR 评审 |
| `schema_extra` 只对开发者角色开放 | 权限点 + 审计（26.2、26.5） |
