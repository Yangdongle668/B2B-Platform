## 背景

失效删除之后，已在途的旧回源可能重新写入；BufferStore 的取出即删除语义不能保证 CDN 失效可靠完成。

## 决策

Redis 站点代次保护读写，invalidate 先推进代次，getOrLoad 比较回源前代次后原子回填。Event Publication Registry 直到 Redis 与 CDN 都成功才完成；V1 不把去抖缓冲当可靠队列。

动态HTML、重定向、404/410、搜索壳与sitemap/robots沿用同一freshUntil预算：浏览器必须重验，CDN剩余TTL不超过min(55秒, freshUntil-now)，没有可信到期时间则no-store。禁止stale扩展重新延长旧内容寿命；只有带哈希静态资源可以长期immutable。

M0-07C原型反馈：读、capture、写和恢复门闩在Redis端原子核对本次server run_id与恢复epoch；从RDB恢复的旧ready/代次也不能复活旧token。恢复先关闭缓存读写、轮换epoch并重投边界内失效义务，再按恢复token放行；token过期的恢复者不得开闸。原型已验证真实Redis7.4.11的RDB恢复及过期恢复者拒绝；恢复pending检查仅在静止源写夹具下执行，正式协调器仍须持久记录恢复边界，不能将一次查询视为跨存储原子屏障。单节点内部机制不新增跨模块接口或采纳状态，Cluster/ACL/容量另验。

完整签名、事务边界、失败恢复与适配器约束统一在[平台框架 4.10.3](../framework/platform-framework.md)登记。本 ADR 解释决策理由，不另建跨模块契约定义。问题映射和故障验收见[处理说明](../reviews/design-issue-resolution-2026-10-20.md)。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 本文方案 | 明确事实提交和派生状态的边界，可恢复、可测试 | V1 使用粗粒度站点代次，失效时额外回源；必须监控负载并验证端到端 TTL 预算。 | 提议采用，待评审 |
| 仅按 tag 删除或给 loader 加租约 | 初期改动较少 | 删除不阻止旧 loader 回填；租约过期也不提供版本保护。 | 不采用 |

## 后果

### 正面

- 将 DELIVERY-02 从笼统待定项整理为具体设计，保持业务模块只访问自己的表。
- 并发、重试和宕机结果可由数据库/端口行为验证，不以文档审查代替运行测试。

### 负面与代价

- V1 使用粗粒度站点代次，失效时额外回源；必须监控负载并验证端到端 TTL 预算。
- 新增契约、真实实现、替身及契约测试需同批实现；本仓库尚无代码骨架。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 只通过平台框架登记的契约协作；站点边界不变 | 架构负责人评审、ArchUnit、Modulith verify |
| 必须执行本方案的并发/故障时序 | 处理说明中的契约、集成与故障注入用例 |
| ADR 不自动获得 Accepted 状态 | 按 [ADR 流程](README.md)及框架 4.9 评审；此轮仅起草方案 |
