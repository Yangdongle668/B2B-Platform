# ADR-009：站点与语言模型（不设租户层）

| 项 | 内容 |
|---|---|
| 状态 | Accepted（已确认） |

| 相关 ADR | ADR-001、ADR-005、ADR-010、ADR-012、ADR-013、ADR-015、ADR-017 |

## 背景

- V1.0 只预留了 `tenant_id`，没有设计站点与语言（0.2 第 13 项）。
- **产品形态已确认为自用**（0.4 A1、32 章 Q1）：一次部署服务一家企业；企业可以有多个品牌站或国家站（如 `brand-a.com`、`brand-b.de`）；不做 SaaS，不为其他企业交付。
- 目标市场为欧盟、英国与北美；内容以简体中文录入，前台 V1 先只开放中文，其他语言由 AI 翻译生成后按需开放（0.4 A2、32 章 Q2，ADR-005、ADR-017）。单站 ≤ 10 种语言（A4）。
- 站点之间的隔离必须覆盖所有存储与缓存：MySQL、Redis、对象存储、Meilisearch、CDN，以及日志与指标（5.3）。
- 后台用户可能在多个站点工作，但只能访问自己有角色的站点。

## 决策

1. **两级上下文 Site → Locale，不设租户层**（5.1）。一次部署 = 一家企业；站点（Site）是最高隔离单位，每个站点有自己的域名、语言、模块启用状态、主题与站点资料：

```text
User（用户：全局唯一，不属于某个站点）
Site（站点：主域名、主题、默认对外语言、URL 策略、时区）
 ├── SiteDomain（主域名 / 别名域名 / V2：语言独立域名）
 ├── SiteLocale（站点语言：URL 前缀、hreflang 值、是否对外公开、是否自动翻译、排序）
 ├── SiteModule（站点启用的模块，见 ADR-001）
 ├── SiteProfile（站点资料：公司信息、Logo、联系方式、法定信息，见 16.3）
 └── UserSiteRole（用户在该站点的角色）
```

   对应表：`sys_site`、`sys_site_domain`、`sys_site_locale`、`sys_site_module`、`sys_site_profile`、`sys_user_site_role`（25.8）。

2. **用户与角色**：用户全局唯一；角色按站点分配；系统管理员管理站点、模块与系统设置，拥有所有站点的权限（5.1、26.2）。

3. **站点语言**（5.1、5.4）：
   - 源语言固定为简体中文 `zh-CN`（即 `cnt_content.primary_locale`）。
   - 每个站点语言有“对外公开”与“自动翻译”两个设置：未对外公开的语言只能在后台与预览中查看，不出现在前台、语言切换器、hreflang 与 sitemap 中；开放新语言只需修改站点语言设置，不需要改代码。V1 默认只有 `zh-CN` 对外公开。
   - `sys_site.default_locale`（默认对外语言）是根路径 302 跳转与 `x-default` 的目标，必须是对外公开的语言；URL 规则见 ADR-005。
   - V1 的 URL 策略固定为子目录（全部语言带前缀）；V2 可选语言独立域名（`sys_site_domain.type = LOCALE`）。

4. **请求上下文**（5.2）：

| 场景 | 解析方式 |
|---|---|
| 前台（Nuxt → Delivery） | Nuxt 把 Host 放入 `X-Site-Host`，连同内部令牌发给后端；`SiteResolver` 按域名找到站点；路径前缀决定语言；别名域名或 http 301 到主域名 https |
| 前台（浏览器 → Public API） | 反向代理透传 Host 与真实 IP，按同样方式解析 |
| 后台 | 请求头 `X-Site-Id`；后端校验用户在该站点有角色 |
| 异步任务与事件 | 显式携带 `siteId`（系统级为空），执行前设置上下文 |

   上下文保存在 `RequestContext`（ScopedValue / ThreadLocal）中，通过 `TaskDecorator` 传递给异步线程。

5. **站点隔离**（5.3、25.7）：

| 资源 | 隔离方式 |
|---|---|
| MySQL | 站点级表带 `site_id`；MyBatis-Plus 行级拦截器（`TenantLineInnerInterceptor`，列名配置为 `site_id`；类名只是框架命名）自动追加条件；全局表（`sys_user`、`sys_user_mfa`、`sys_role`、`sys_permission`、`sys_module`、`sys_dsr_request`、系统级设置等）列入豁免清单；`sys_audit_log` 的 `site_id` 可空，同样豁免 |
| Redis | Key 前缀 `s{siteId}:…`；系统级数据 `sys:…` |
| 对象存储 | 路径 `{siteId}/{yyyy}/{mm}/…`；公开桶与私有桶分离 |
| Meilisearch | 每个站点的每种语言一个索引 `s{site}_{locale}_content`（19） |
| CDN Cache Tag | 前缀 `s{siteId}:…`（23.2） |
| 日志、指标与链路追踪 | 带 site 维度 |
| 后台会话 | 会话绑定用户；切换站点时校验用户在该站点有角色 |

   跨站点查询只允许出现在系统管理接口中。

6. **未来多企业**：采用“一企业一实例”独立部署（独立数据库与存储），不在一套部署中共享多家企业的数据（5.3、27.1）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 保留租户层（Tenant → Site → Locale） | 便于以后做 SaaS | 自用场景下多一个隔离与权限维度，所有表、查询、缓存键、测试都要多处理一层 | 不采用：与已确认的 A1 不符 |
| 每个站点独立部署一套系统 | 隔离最彻底 | 环境、升级、备份的运维成本按站点倍增；用户、角色、模块无法跨站点统一管理 | 不采用 |
| 每个站点一个独立数据库或 schema | 数据库层面隔离 | 迁移、连接池、备份按站点倍增；跨站点的系统管理复杂 | 不采用 |
| 语言作为全局配置，所有站点共用 | 配置简单 | 品牌站、国家站无法各自决定开放哪些语言与默认对外语言 | 不采用 |
| 单库共享表 + `site_id` 行级过滤，其他资源按站点前缀隔离；Site → Locale 两级；多企业时一企业一实例 | 结构简单；一套部署管理企业的全部站点 | 隔离依赖拦截器、豁免清单与测试 | 采用 |

## 后果

### 正面

- 数据模型与权限模型比多租户简单；一套生产环境管理企业的全部站点（27.1）。
- 用户全局唯一，可以在不同站点担任不同角色。
- 每个站点独立启用模块、选择主题、配置语言；开放新语言只改站点设置（1.3 S11）。
- 所有资源按同一种站点前缀规则隔离，便于排查、清理与按站点失效缓存。

### 负面与代价

- 隔离依赖行级拦截器与豁免清单：遗漏 `site_id`、把站点级表错误地列入豁免清单、或绕过拦截器的 SQL，都可能造成越权，必须由自动化测试兜底。
- 所有站点共享数据库与运行资源，某个站点的大批量导入或批量翻译会占用共享资源。
- 未来如需服务其他企业，只能一企业一实例部署，每多一家企业就多一套运维。
- V1 只有子目录 URL 策略，语言独立域名要到 V2。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 不引入租户层或 `tenant_id` 字段 | PR 评审（CLAUDE.md 禁止 10） |
| 新建站点级表必须带 `site_id`；新建全局表必须列入 25.7 的豁免清单，并在 PR 中说明 | PR 评审；《领域模型与数据库设计》同步更新 |
| 跨站点查询只允许出现在系统管理接口中，不得绕过行级拦截器 | 站点隔离测试（28）；PR 评审 |
| 站点隔离测试：准备两个站点的数据与只在其中一个站点有角色的用户，遍历后台接口，验证不能越权读写 | CI 专用测试套件，必须通过（5.3、28） |
| Redis key、对象存储路径、Meilisearch 索引名、Cache Tag 必须带站点前缀 | PR 评审；站点隔离测试 |
| 领域事件（`DomainEvent.siteId`）与异步任务必须携带 `siteId`，执行器在运行前设置上下文 | PR 评审；模块集成测试（28） |
| 后台权限在后端校验（`@RequiresPermission` + 数据范围），切换站点时校验用户在该站点有角色 | 站点隔离测试；PR 评审（26.2） |
| 开放或关闭语言通过站点语言设置完成，不为某个语言写特殊代码 | PR 评审 |
