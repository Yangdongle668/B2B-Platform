## 背景

- 领域事件是模块协作的三种方式之一（ADR-002）。以“发布”为例，一次发布之后要清除 Redis 与 CDN 缓存、更新 sitemap、推送 IndexNow、重建链接索引、执行 SEO 健康检查、增量重算图谱、更新搜索索引、更新媒体引用；源语言发布后还要为目标语言创建翻译任务（4.3、4.4、5.7）。
- 一致性要求（4.4、1.5）：
  - **强一致**：内容状态、快照、投影、路由与重定向在同一个数据库事务中完成，保证“发布成功即可被路由”；
  - **最终一致**：缓存、sitemap、图谱、搜索、引用在 60 秒内完成；目标语言译文在 5 分钟内生成（不含人工审校）；AI 引擎故障不影响中文内容的发布（5.7）。
- 如果订阅方在发布事务内同步执行，任何一个下游（CDN、Meilisearch、AI 引擎）失败都会导致发布回滚；如果只在事务提交后普通地异步通知，进程在提交后崩溃或监听器失败时事件会丢失。V1.0 没有可靠性设计（0.2 第 10 项）。
- 不采用微服务，V1 不引入消息队列（2.1）。

## 决策

采用 **事务提交后投递 + Spring Modulith Event Publication Registry（数据库 Outbox）**，V1 不引入 MQ（4.1）：

| 方面 | 决策 |
|---|---|
| 发布 | 应用服务在业务事务内调用 `ApplicationEventPublisher.publishEvent(event)` |
| 投递 | 监听器使用 `@ApplicationModuleListener`：事务提交后异步执行，并在新事务中运行 |
| 可靠性 | Event Publication Registry 在发布事务中把事件写入 `event_publication` 表；监听器成功后标记完成；未完成的事件在启动时与定时任务中重新投递（**至少一次**） |
| 幂等 | 所有监听器必须幂等：按 `eventId` 去重，或采用天然幂等的 upsert |
| 顺序 | 不保证全局顺序；同一内容的事件携带 `revisionNo` 与 `occurredAt`，监听器丢弃过期事件 |
| 模块停用 | 监听器包装器检查站点启用状态，停用时跳过执行；事件本身照常记录（3.8） |
| 监控 | 未完成事件的数量与最早时间纳入指标；数量 > 100 或最早一条超过 10 分钟时 P2 告警（27.4） |
| 外部化 | V2 需要时通过 Modulith 事件外部化到 Kafka / RabbitMQ，业务代码不变 |

事件结构（4.2）：

```java
public interface DomainEvent {
    String  eventId();        // TSID（ADR-014）
    int     schemaVersion();  // 事件结构版本
    Instant occurredAt();
    Long    siteId();         // 可空：系统级事件为空
    String  actor();          // 用户 ID，或 "system"
}
```

- 命名为 `<聚合><过去分词>Event`；事件只携带 ID 与必要的事实，订阅方需要更多数据时调用服务接口。
- 内容类事件统一为 `ContentPublishedEvent(contentType = …)` 等，订阅方不依赖具体业务模块。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 同步监听：订阅方在发布事务内执行 | 简单，强一致 | 任一下游失败导致发布回滚；发布耗时随订阅方增加；把 CDN、搜索、AI 引擎的可用性绑到发布上 | 不采用 |
| 事务提交后的普通异步事件，无登记 | 简单，无额外表 | 提交后进程崩溃或监听器失败时事件丢失，无法重试与监控 | 不采用 |
| 引入消息队列（Kafka / RabbitMQ）+ Outbox | 高吞吐、可重放、可跨服务 | 新增基础设施与运维成本；模块化单体内没有必要 | V1 不采用；V2 需要时外部化 |
| 事务后投递 + Event Publication Registry | 不丢事件；下游失败不影响发布；无需新增基础设施；保留演进到 MQ 的路径 | 至少一次投递要求幂等；`event_publication` 带来额外写入 | 采用 |

## 后果

### 正面

- 发布之后的所有后续处理都不会丢失，并且各自独立重试；下游故障（CDN、Meilisearch、AI 引擎）不阻塞发布。
- 不需要新的基础设施，事件状态可以用 SQL 查询，便于排查。
- 将来外部化到 MQ 时业务代码不变。

### 负面与代价

- 至少一次投递：所有监听器都必须幂等，否则会重复执行（如重复推送、重复翻译）。
- 不保证全局顺序：监听器必须用 `revisionNo` 等字段识别并丢弃过期事件。
- 最终一致：后续处理有延迟（缓存、sitemap 等 60 秒内，译文 5 分钟内），后台需要正确展示中间状态（如翻译状态 `QUEUED`）。
- `event_publication` 表持续增长，已完成记录的清理方式需要在详细设计中确定。
- 异步流程的调试与测试更复杂，需要 Scenario API 等测试手段。

### 需要遵守的规则

| 规则 | 检查方式 |
|---|---|
| 事件在业务事务内发布；不在事务外补发，不绕过 Event Publication Registry | PR 评审 |
| 跨模块订阅使用 `@ApplicationModuleListener`，不在发布事务内同步执行其他模块的逻辑（如在发布事务中同步调用 AI 引擎） | PR 评审 |
| 监听器幂等（`eventId` 去重或 upsert），并丢弃过期事件 | PR 评审；模块集成测试：`@ApplicationModuleTest` + Scenario API 覆盖事件场景（28） |
| 事件定义在 `platform-api`；只做兼容的新增，不兼容的变更提升 `schemaVersion` 并在过渡期同时支持新旧版本 | CODEOWNERS（架构负责人审核） |
| 模块发布与订阅的事件在 `module.json` 中声明并与代码一致 | CI 脚本（29.3） |
| 未完成事件纳入告警 | 27.4 的告警规则 |
| 引入 MQ 属于新的基础设施依赖，需要新的 ADR | 29.5 |
